# Bucket Prompts

Use these prompts when spawning subagents. Each agent should inspect only its assigned bucket and return findings with severity, confidence (high/medium/low), file/line, the quoted added diff line(s) as evidence, a minimal suggested fix or the exact test that would pin the behavior, and suggested verification.

## Instantiation contract

These bucket texts are templates, not dispatch prompts. Every dispatched prompt must add, on top of the bucket text:

1. The PR goal in one or two sentences, the changed-file list, and where to read the full diff and the current files.
2. Numbered probes specific to this diff: concrete files, symbols, grants, schemas, and invariants to check, derived from the diff and from the Required Enumerations raw material (`scripts/enumerations.py` output). Generic dispatch produces generic review regardless of model quality.
3. The instruction to answer every numbered probe explicitly. "No finding" for a probe is only acceptable with a statement of what was checked. An output that skips a probe is an incomplete bucket.
4. The required output format (severity, confidence, file:line, quoted added lines, minimal fix or pinning test), and an explicit "top N things checked hardest" list when there are no findings.

Do not seed the prompt with your suspected answers; give raw context and probes, not conclusions.

## Correctness/logic

Review the added and changed lines for line-level logic defects, the way a careful human reviewer reads each diff hunk. Check inverted or wrong conditions, wrong variable after copy-paste (especially in near-duplicate branches or paired min/max, low/high, first/last logic), missing `await`/`return`, null/undefined/None dereference on optional values, off-by-one in loops/slices/boundaries, operator precedence mistakes, unreachable code, and switch/match branches that fall through or return the wrong value. Check error handling: swallowed exceptions, overly broad catch clauses, error paths that return success-shaped values, and cleanup skipped on early return (unclosed files/connections, missing finally/defer/context manager). Check redundant or expensive work inside loops. Check consistency with the surrounding repo: duplicated logic where an existing helper already exists, naming or patterns that diverge from sibling code, and misuse of repo utilities. For every exported/shared function whose behavior changed, enumerate ALL its call sites — including files the diff does not touch and barrel re-exports — and classify each as updated, unaffected (say why), or affected-and-unhandled; do not sample. Quote the exact added line for every finding and propose the minimal fix or the test that would catch it.

## UI/state/accessibility

Review the diff for UI state, accessibility, and visual regressions. Check desktop/mobile behavior, loading/error/empty states, feature flags, disabled/pending/stopping states, old affordances after actions move, accessible names, `aria-*`, icon-only controls, truncation, flex shrink, stale CSS modifier names, and keyboard interaction. For async detail views, verify rendered data still matches the current selected target, not merely that some previous detail is non-null. For step/guard/check displays, distinguish `not-run` from `pass` when evaluation short-circuits. For clickable rows or containers, ensure there is a real button/link activation path and nested controls do not bubble into parent handlers. Ignore unrelated backend concerns.

## Tests

Review the diff for test coverage and test truthfulness. Compare changed test names against actual fixtures and assertions. Flag broad names that only exercise one shape, missing focused regression tests near existing coverage, tests that mock the wrong contract, leaked globals, unsound helper types, or implementation-only assertions. When matching external output back to source data, expect a fixture where otherwise valid strings differ by casing, surrounding whitespace, punctuation, diacritics, or Unicode compatibility form when the behavior claims formatting-tolerant matching. For prompt sentinels, placeholders, JSON-only LLM responses, or exact-output strings, require a regression fixture with expected model decoration such as case changes, leading bullets, code fences, whitespace, commentary before/after JSON, or trailing punctuation. For paired fields or validation paths, require asymmetric fixtures where only one side is present. Name the exact behavior a test should pin.

## Data/order/bounds

Review data reads and transformations for pagination, ordering, date clocks, and bounds. Check database/API query limits, page caps, latest/current/prior semantics, filter-before-limit ordering, stop conditions matching API sort order, blank/invalid external data, duplicate rows, nested scans over large collections, and future/past date boundaries. Watch for full scans or expensive setup on search/filter/pagination endpoints; cache stable options or move work behind branches that actually need it.

## Async/idempotency

Review async lifecycle, retries, cancellation, and idempotency. Check work racing without cancellation, in-flight work mutating after timeout, double-click/retry paths before `await`, pending/stopping/launching state confusion, retryable writes, idempotent upserts, duplicate actions/rows, timers, abort signals, and retry backoff behavior.

## Observability

Review diagnostics and telemetry. Check every catch/fallback/skip for sanitized actionable fields: error message, stack when safe, validation issues, API response messages, relevant IDs, and production-debug usefulness. Check alert/webhook environment gates and analytics/event docs against emitted properties and distinct IDs.

## Contracts/schema

Review API, validation, parser, generated declarations, package manifests, persisted rows, and external-data contracts. Check optional external fields, inconsistent request fields, lifecycle-state modeling, schema descriptions, generated artifacts, backward compatibility, and whether tests cover the contract rather than implementation details. Check external/provider/parser strings that are used as identifiers, join keys, or de-duplication keys; if schemas accept plain strings, verify comparisons normalize or canonicalize casing, whitespace, punctuation, diacritics, Unicode compatibility forms, non-ASCII letters/digits, and known aliases before strict equality. When a prompt/spec introduces a sentinel, placeholder, JSON-only response, or exact output string, review every downstream consumer that treats non-empty strings as real data, cache hits, UI enablement, persistence, side-effect input, or ingestion input. JSON-only LLM prompts must not teach code fences, prose commentary, contradictory examples, or shape variants that the parser/schema rejects. Sentinel and JSON extraction should tolerate expected model decorations such as case changes, leading bullets, backticks, code fences, whitespace, commentary, and trailing punctuation when the product depends on recovery. Helpers named for a specific category, template, state, or lifecycle branch must assert that precondition before writing or mutating persisted state. Validation diagnostics should attach issues to the actual offending field or fields; for paired keys/fields, check both asymmetric cases. Dependency manifests are contracts too; open-ended compatibility ranges should be intentional for the manifest format being reviewed. Require regression tests for case/whitespace/sentinel variants when a valid match could otherwise be dropped or a placeholder could be ingested.

## Privacy/prod-safety

Review sensitive data, credentials, and production safety. Check scripts and workers touching production systems, exports, customer/user/patient data, payment data, credentials, storage buckets, or logs. Flag production writes without explicit opt-in, wrong-environment credential risks, raw sensitive data in non-ignored paths, concrete secret names in docs, and overstated "no sensitive data" claims.

## Security

Review exploitability and trust-boundary failures. Check auth/authz, tenant/clinic/user boundary enforcement, trusting client-supplied IDs, missing ownership filters, unsafe redirects, SSRF or arbitrary URL fetches, file/path/upload/download handling, unsafe HTML or markdown rendering, XSS, CSRF, CORS/cache headers, secret/session/token exposure, logs that expose credentials, injection into SQL/NoSQL/query builders/templates/prompts, risky dependency or config permission changes, IAM/serverless permissions, and model output treated as trusted input. When the diff adds access to an external resource or changes permissions/roles (cloud IAM, database grants, service accounts, API scopes), build the capability-parity table: every code path that newly reaches the resource x every independently deployed runtime that executes it (each serverless function, service, app server, worker, script) x the grant or credential evidence at file:line, or MISSING — a grant to one sibling runtime is not evidence for another, and a grant to an identity the runtime does not authenticate as counts as MISSING. Itemize every new grant: identity, actions, resource scope, and whether each is needed. For LLM code, check prompt-injection paths, strict output parsing, schema validation, tool/action execution gates, and whether untrusted model text can trigger side effects or persisted unsafe state. Return only plausible, diff-grounded security findings; do not dilute with generic best practices.

## Docs/truthfulness

Review docs, comments, PR descriptions, and source provenance. Check for local paths, usernames, `Downloads`/`Desktop`, "this machine", unreproducible source references, tool-specific process requirements in project docs, comments that describe old behavior, headings with adjacent duplicate words, docs snippets that do not match actual function signatures, PR descriptions claiming helper reuse when logic is duplicated, and test names that overclaim coverage. When docs and code change together, extract every normative sentence from the added/changed docs (contains "overwrites", "prefers", "guarantees", "must", "will", "grants", "falls back") and map each to code evidence at file:line: agrees, disagrees, or not implemented — report the full mapping, not just the mismatches you noticed. Also verify the PR description lists every externally observable behavior change in the diff (new error responses, new authz gates, changed status codes); an unlisted behavior change is a finding. Flag typos in user-facing strings, public identifiers, and doc prose. When docs and implementation change together, compare discriminator fields, lifecycle states, source-of-truth predicates, generated artifacts, API names, and examples across RFCs, ADRs, plans, code, and tests. Flag any doc that describes an older predicate or field name than the implementation uses. If a design doc intentionally changes issue acceptance criteria, require an explicit named section explaining the change. If copy or prose review comments are rejected because a source of truth approved the wording, verify that source is named and classify the thread as an intentional `explain`, not an unresolved loose end.

## Adversarial integration review

Run this after focused buckets. Assume the PR still contains a subtle bug or reviewer-obvious gap and try to break the whole change, not one file. Mandatory probes: (a) quote the PR's core invariant verbatim, then find every OTHER writer and reader of the same rows/objects/keys — changed or not — and check each against the invariant; unchanged writers the PR newly exposes are the classic miss; (b) for every function whose behavior changed, hunt for callers in unchanged files whose assumptions now break; (c) trace one full production request/event through the new code per major path, naming the runtime and its permissions at each hop. Compare the claimed PR goal, issue/design docs, tests, schemas, prompts, generated artifacts, lifecycle states, side effects, and implementation. Look for contradictions between surfaces, missing edge cases that make the happy path untrue, misleading validation or logs, unsafe defaults, duplicate side effects, stale state, parser/schema mismatch, docs that promise more than code proves, and places where a reviewer would reasonably ask "what happens when this input is malformed, missing, duplicated, stale, reordered, unauthorized, or model-decorated?" Return the top plausible breakages with file/line evidence and the test or check that would prove each one. If no findings remain, return the top 3 challenges considered and why the current diff covers them.
